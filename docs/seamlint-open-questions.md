# Seamlint 未決事項メモ(対応点・ノッチまわり)

## このメモの位置づけ

このファイルは、[seamlint-mvp-and-loomit-integration.md](./seamlint-mvp-and-loomit-integration.md) の「判断保留 > ノッチやボタン位置を SVG 側でどう表すか」を掘り下げた結果、**方針は決まったが詳細がまだ詰まっていない点**を残すためのメモである。

きっかけは「袖山とアームホールを縫い合わせるとき、端点(袖山の天・谷、身頃の肩点・脇点)がどこに対応するのか幾何から決められるのか?」という問い。後ろ身頃が大きく肩線が前に出るデザインなどでは、袖山の頂点がどの身頃点に対応するかはデザインの決めごとであり、カーブの形からは復元できない、というのが出発点。

## 確定した前提(このメモの土台)

以下は今回の議論で「決定」として扱ってよい方針。詳細検討は次節以降。

1. **接続を2つの位相に分ける。**
   - **point-join**: 2本が1点を共有して続く(プリンセスライン、ヨーク線、切り替えが滑らかに続く線)。対応点は共有点そのもので自明。→ Rule 3(端点+接線)が正しく効く範囲。
   - **seam-join**: 2本が辺の長さ全体で縫い合わさる(袖山↔アームホール、肩線、脇線、袖口↔カフス)。対応点は幾何から出ない。→ Rule 3 は使わない。

2. **対応点は「計算するもの」ではなく「データとして与えるもの」。**
   洋裁が合印(ノッチ)を打つのは、対応がカーブの形からは出ないから。前ノッチ・後ろノッチ・天↔肩点、のように人間が対応を宣言する。Seamlint はこれを推定しない。

3. **Seamlint が読むのは SVG(座標列)であって `.val` ではない。**
   名前付きの点(肩点、袖山頂点)は `.val` 側には存在しうるが、SVG にエクスポートした時点で意味情報は落ちる。今の Seamlint には対応点の意味情報が届いていない。

4. **検査を「対応点が要る/要らない」で二分する。**
   - 対応点 **不要**(今できる): 総長、長さ差(=いせ量)、いせ比率の妥当性。
   - 対応点 **必須**(ノッチ入力後): いせの分布、ノッチ間の対応、対応点での向き一致。

5. **袖山↔アームホールに対する現時点の正解は「長さ・いせ量だけ見る」。**
   対応点ゼロで成立し、洋裁的にも意味がある(いせ過多/過少の警告)。

6. **天・尾根の自動検出は"ヒント"止まり。**
   最高点や最大曲率点を「合印候補では?」と提案するのは read-only 哲学に合うが、"ここが対応点だ"と断定はしない。

## まだ詰める必要がある点

### A. ノッチ/合印をどこに、どう表すか

対応点情報の"入り口"をどこにするか未決。候補:

- SVG 側にマーカーとして埋める(別要素、`id` 付きの点、`data-*` 属性など)。
- Loomit の connector メタデータで持つ(`connectors.*.ranges` の正規化位置 from/to がこの器になりうる)。
- `.val` から抽出する経路を将来足す。

→ どれを正とするか、複数許すか、正規化位置(0–1)か実座標かを決める必要がある。

### B. `.val` → SVG エクスポートでノッチが残るか(要実機確認)

`.val`(Valentina/Seamly2D)のノッチ/passmark が SVG エクスポートに保持されるかは未確認。実際のエクスポート結果を1つ用意して確かめる。残らないなら、対応点は Loomit メタデータ経由が本線になる。

### C. ノッチ対応のデータモデル

型と例だけ先に決める(実装は後)。イメージ:

```text
seam = A辺 と B辺 の、順序付きノッチ対応リスト。
       各ノッチは A/B 上の位置(正規化 or 実座標)を持つ。
       隣り合うノッチ間の区間ごとに、長さペアと behavior(plain / ease / gather)を持つ。
```

- `GeometryCheckSpec`(integration contract)にノッチ対応をどう足すか。
- 天は「肩点として指定されたノッチ」というラベル付き入力。推定しない。
- ノッチ数が A/B で食い違うときの扱い(error か warning か)。

### D. 天/尾根の自動検出をヒントとして出すか

出すなら:

- 何を根拠にするか(最高点 / 最大曲率 / 端からの弧長)。
- 出力の位置づけ(`info` 診断? 提案のみ?)。断定しないことを担保する。
- 対応点が入力で与えられている場合は自動検出を無効化するのか。

### E. join_kind による Rule 適用ガード

`join_kind` 導入時に、接続種別ごとに回すルールを切り替える。特に:

- `sewn-seam` / `eased-seam` に接線チェック(Rule 3)を**回さない**ガード。
- 現状 `--expect-smooth` は任意の2本に接線チェックを回せてしまう(point-join 専用のつもりだが強制はしていない)。join_kind でここを形式化する。

### F. いせ量ルール(`ease_amount_out_of_range`)

対応点不要で今すぐ書けるが、閾値設計が未決:

- いせ量(長さ差)の許容レンジ、いせ比率レンジ(docs 例: ease_ratio [0.02, 0.08])。
- `eased-seam` と `sewn-seam` で閾値を分けるか。
- いせ"分布"の検査はノッチ必須なので、まずは総量のみ。

### G. Rule 3 の scoping 明示

Rule 3(`endpointTangentCompatibility` / `--expect-smooth`)は **point-join 専用**であることを、コード・usage・docs のどこかで明示する。袖↔身頃に使うのはカテゴリエラー。

## 今できること / できないことの線引き

| 検査 | 対応点 | 状態 |
| --- | --- | --- |
| 単独カーブの折れ・閉じ忘れ(Rule 1) | 不要 | 実装済み |
| point-join の端点ギャップ・接線一致(Rule 3) | 共有点で自明 | 実装済み |
| seam の総長・長さ差(Rule 2) | 不要 | 実装済み |
| いせ量が妥当か(`ease_amount_out_of_range`) | 不要 | 未実装(F) |
| いせの分布・ノッチ間対応・対応点の向き | 必須 | ノッチ入力待ち(A–C) |
| 天/尾根の推定 | ―― | 幾何からは断定不可。ヒント止まり(D) |
